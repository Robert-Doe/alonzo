PREREQUISITE P2

Variables, Binding & Scope

Almost every bug in a λ-calculus implementation is a bug about which x an x refers to. This page gives you the words to talk about that precisely.

P2.1A binder introduces a name

In λx. x y, the λx part is a binder: it introduces the name x. The part after the dot, x y, is its body, which is also the binder's scope: the region of text where that name means "this λ's parameter."

A binder is a name tag handed out at the door of a room.

Inside the room (the body), anyone saying "x" means the guest wearing the x tag. Outside the room, that tag means nothing. Another room can hand out its own x tag to a completely different guest.

P2.2Bound vs free occurrences

Each occurrence (each place a variable is used) is one of two kinds:

  • Bound: it sits inside the scope of a binder with the same name. In λx. x y, the x in the body is bound.
  • Free: no enclosing binder has its name. In λx. x y, y is free. Its meaning comes from outside the term.

Free-ness is relative to a term. In x y alone, x is free. Wrap it in λx. and the same occurrence becomes bound.

Sharpen your pencil

In (λx. x z) (λy. x y), mark each variable occurrence as free or bound.

Answer: the first x is bound (by the first λ). z is free. In the second function, y is bound, but that x is free: the first λ's scope ended at its closing parenthesis.

P2.3Shadowing: the innermost binder wins

In λx. λx. x, which binder does the final x belong to? The nearest enclosing one, the inner λ. The outer x is shadowed: still there, but unreachable by that name inside the inner scope. This is exactly how nested functions in JavaScript, Python and C behave.

P2.4Lexical (static) scope

"Which binder does this name refer to?" is answered by looking at the text, the nesting of the program as written. It is never answered by what happens at runtime. That is lexical scope, and the λ-calculus has it by definition. Early LISP (1960) used dynamic scope instead and got some programs wrong. You'll rebuild that bug in Track H5 and fix it with closures from Module 19.

P2.5Bound names don't matter

λx. x and λy. y are the same function: both return their argument. Renaming a binder together with all the occurrences it binds changes nothing. This is called α-conversion (Module 4). Free names do matter: λx. y and λx. z are different, because they refer to different things outside.

Watch it!

Renaming must not capture. Rename the binder of λx. y to y and you get λy. y, the identity function. The free y got grabbed by the new binder. Avoiding this is the whole job of Module 5.

P2.6Where this shows up

  • Module 1: the abstraction node stores the binder's name.
  • Module 4: computes the free variables and decides α-equivalence.
  • Module 5: substitution that never captures.
  • Module 6: de Bruijn indices, which replace names with "how many binders out."
  • Module 19, C7: environments and closures, which are scope made concrete at runtime.
