MODULE 05

Capture-Avoiding Substitution

M[x := N] ("put N wherever x appears free in M") is the single operation that all of computation will run on. Its obvious implementation is wrong in a way that's easy to miss.

01The Big Analogy

Substitution is mail-merge, and capture is the letter that reaches the wrong person.

You have a form letter M with a blank marked x, and a value N to paste in. Paste N into every blank, except blanks inside a quoted inner document that defines its own "x" (shadowing). Those aren't your blanks.

Now the danger. Your value N says "give this to y," meaning the y in your office. But one section of the letter is addressed to a family whose house rule is "here, y means our houseguest" (a λy). Paste N in there unchanged and the message now goes to the houseguest. The text reads fine and the meaning is wrong.

The fix is polite and mechanical. Before pasting, ask that family to rename their houseguest's nickname to something nobody uses (y1). Their internal meaning doesn't change (α-conversion, Module 4), and now "y" in your message can only mean your y.

02What Happens, Step by Step

  1. subst(M, x, N) computes FV(N) once. It's needed at every λ.
  2. At a variable: if it's x, return N. Otherwise return it unchanged.
  3. At an application: substitute in both sides. If neither changed, return the original node (sharing).
  4. At λx. P: stop. This λ shadows x, so there are no free x's below.
  5. At λy. P where x isn't free in P: stop too. Nothing to replace.
  6. At λy. P where N doesn't mention a free y: no capture is possible, so go into P.
  7. Otherwise, danger. Pick a fresh z that is free in neither N nor P and isn't x. Rename λy. P to λz. P[y := z], then go into it.

04The Code, Explained

The naive version: one missing check

src/subst.ts

case "lam":
  if (m.param === x) return m;                          // x is shadowed: nothing to replace below
  return Lam(m.param, substNaive(m.body, x, n));        // BUG: if m.param is free in n, it gets captured

It respects shadowing, so it's not obviously wrong. It just walks N into a binder's scope without asking whether N mentions that binder's name.

The capture-avoiding λ case

case "lam": {
  if (m.param === x) return m;
  const fvBody = freeVars(m.body);
  if (!fvBody.has(x)) return m;                             // nothing to substitute below: share
  if (!fvN.has(m.param)) return Lam(m.param, go(m.body));   // no capture possible
  // Capture danger: rename the binder to z, which is free in neither N nor the body, and isn't x.
  const avoid = new Set([...fvN, ...fvBody, x]);
  const z = freshName(m.param, avoid);
  log?.renames.push({ from: m.param, to: z });
  return Lam(z, go(subst(m.body, m.param, Var(z), log)));
}

Three escapes, then the repair. Why must z avoid the body's own free variables? Take (λy. x y1)[x := y]. Renaming y to y1 would capture the body's free y1, so the engine skips to y2. That's in the demo output.

Fresh names

export function freshName(base: string, avoid: Set<string>): string {
  if (!avoid.has(base)) return base;
  const stem = base.replace(/\d+$/, "");
  for (let i = 1; ; i++) { const c = `${stem}${i}`; if (!avoid.has(c)) return c; }
}
BULLET POINTS
  • Substitution replaces free occurrences only, and stops at a shadowing binder.
  • Capture: N's free variable lands under a binder with the same name.
  • The fix is α-conversion on demand: rename the obstructing binder to a fresh name, then continue.
  • Checking free variables before and after does not detect all captures (the Brain Exercise).

05Limits: What You Cannot Do Yet

Can't do yet

  • Compute. Substitution is the tool for β-reduction, but nothing applies a function yet (Modules 7–8).
  • Avoid the cost of freeVars at every λ. It's recomputed each time, which is fine for small terms and slow for big ones.
  • Skip renaming entirely. With names, fresh-name generation is unavoidable. Module 6 removes names.
  • Substitute several variables at once (simultaneous substitution). Not needed until Module 19.

Can do now

  • Compute M[x := N] correctly for any terms.
  • Show exactly where naive substitution goes wrong, and log the renames that prevent it.
  • Rely on the FV law, α-compatibility and the Substitution Lemma, all tested on random terms.
  • Explain binder / scope / free / bound / capture without mixing them up (vocabulary web).

07Brain Exercise

Think before you reveal

A tempting shortcut for catching capture bugs: "compute FV of the result both ways. If they differ, something got captured." The demo shows this caught only 192 of 414 real captures.

Construct the smallest M and N you can where naive substitution changes the meaning, but the naive and correct results have exactly the same free variables. Explain why the FV check is blind to it.

The Lab's checker verifies your answer
Reveal the answer

Take M = (λy. x) y, x and N = y, i.e. ((λy. x) y)[x := y]:

naive   : (λy. y) y      FV = {y}
correct : (λy1. y) y     FV = {y}

(Verified with the engine: alphaEquivalent says they differ.) The pasted y inside λy was captured. The naive result applies the identity to y, while the correct one applies a constant function. But M already had a free y outside the λ (the argument), so y still shows up in FV either way.

FV is a set of names, and capture is about which occurrence points where. A set can't see that one of two y's changed owner. The robust check is structural: compare binding structure with alphaEquivalent, or use Module 6's de Bruijn indices, where capture can't happen at all.

08There Are No Dumb Questions

Is capture a real-world bug or just a textbook curiosity?

It's real. Macro systems face it: a C preprocessor macro that declares a temporary variable can collide with a caller's variable of the same name. So do hygienic macros in Scheme and Rust, and every compiler pass that inlines functions (Track 2 C9). "Hygiene" is capture-avoidance under another name.

Why not always rename every binder to something fresh? Then capture is impossible.

That works (it's what canonicalize from Module 4 does). But terms become unreadable fast (λv17. v17 v3), and every substitution would allocate a whole new tree. Renaming only when needed keeps output recognizable and shares unchanged subtrees.

Why must the fresh name avoid the body's free variables, not just N's?

Because the renamed binder would capture those. In (λy. x y1)[x := y], renaming to y1 would make the body's free y1 bound. The engine skips to y2. It's in the demo, and it's a classic bug in hand-written substitution.

Does the order matter in P[y := z][x := N]?

Yes. First rename (making room), then substitute. Reversed, you'd push N under the old binder and capture it anyway. The Substitution Lemma test would catch a swapped implementation.

Is there a way to avoid all this renaming?

Yes: get rid of bound names. With de Bruijn indices (Module 6), variables are "the binder k levels out," and capture becomes impossible by construction. The price is index shifting, which has its own classic bugs.

09What's Next

Two modules in a row have fought the same enemy: names. Module 4 needed a special algorithm to see that λx. x and λy. y are equal. Module 5 needed fresh-name generation to stop capture. Module 6 removes the problem at its root. It replaces every bound variable with a number, its de Bruijn index ("how many λs out is my binder?"). α-equivalent terms then become literally identical trees, and substitution needs no renaming, only careful index shifting. It closes Phase 1. After that, the engine is ready to compute.
