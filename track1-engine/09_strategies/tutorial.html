01The Big Analogy

A strategy is a kitchen's rule for which order ticket to cook next.

An order (λx. y) Ω says: "prepare Ω, then throw it away and serve y." And Ω is a dish that is never finished.

  • Applicative order is the careful cook who prepares every ingredient before assembling. They start on Ω and are still cooking at closing time. (Out of fuel.)
  • Normal order reads the outermost ticket first: "throw away the argument, serve y." One step, done.
  • But ask for (λx. x x) (prep z), "use the prepped ingredient twice," and the careful cook preps once and plates twice (2 steps). The outermost-first cook copies the raw ingredient into both plates and preps it twice (3 steps).

Neither rule wins every night. That's the whole story of strict vs lazy evaluation, and this module measures it.

02What Happens, Step by Step

  1. A strategy is a function: given a term, return the redex to contract next, or null if it has nothing more to do.
  2. run(t, strategy, { fuel }) loops: ask the strategy, contract its redex with Module 8's stepAt, and record the step.
  3. It stops with done when the strategy returns null, out-of-fuel after fuel steps, or too-big if the term exceeds the size limit.
  4. It also reports whether the final term is β-normal. For weak strategies, "done" may mean "stopped at a λ or a stuck head."
  5. formatTrace prints each intermediate term with the chosen redex in [brackets].

04The Code, Explained

Four strategies are one-liners over Module 7

src/strategy.ts

export const normalOrder      = { name: "normal order",      pick: t => leftmostOutermost(t) };
export const applicativeOrder = { name: "applicative order", pick: t => leftmostInnermost(t) };
export const callByName       = { name: "call-by-name",      pick: t => weakHeadRedex(t) };
export const headReduction    = { name: "head reduction",    pick: t => headRedex(t) };

All the hard work was naming positions in Module 7. A strategy just picks one.

Call-by-value: Plotkin's evaluation order

function cbvPick(u: Term, path: Step[]): Redex | null {
  if (u.kind !== "app") return null;                                   // a value: nothing to do (never go under λ)
  if (!isValue(u.fn)) return cbvPick(u.fn, [...path, "fn"]);            // function first
  if (!isValue(u.arg)) return cbvPick(u.arg, [...path, "arg"]);         // then the argument
  return u.fn.kind === "lam" ? { kind: "beta", path, term: u } : null;  // (λx. M) V → …;  x V is stuck
}

Running with fuel

for (;;) {
  const r = strategy.pick(cur);
  if (!r) { status = "done"; break; }
  if (n >= fuel) { status = "out-of-fuel"; break; }
  const next = stepAt(cur, r.path, "beta").reduct;
  // … record, count, check size …
}
BULLET POINTS
  • A strategy is just "which redex next?". The step itself is always Module 8's.
  • Normal order is complete: if any strategy finds a normal form, normal order does too (standardization).
  • Applicative order avoids duplicated work, but can die on arguments that are never used.
  • "Out of fuel" is an honest answer. No evaluator can always decide whether a term stops.

05Limits: What You Cannot Do Yet

Can't do yet

  • Get applicative order's efficiency and normal order's completeness. That's call-by-need (Module 22).
  • Prove two paths meet again. So far different strategies' results only happen to agree (Module 10).
  • Run fast: every step re-searches the whole term (machines, Modules 19–22).
  • Decide whether a term will ever stop. Nobody can (Track H3).

Can do now

  • Run any term to completion under five strategies, safely, with fuel and a size cap.
  • Print a trace with each chosen redex marked.
  • Show on 2000 random terms that normal forms are unique, and that normal order finds them whenever applicative order does.

Getting a blank or broken result?
  • "OUT OF FUEL" on a term you think finishes: raise fuel. Out-of-fuel means "not yet", not "never".
  • CBN or CBV "stopped" with redexes left: by design, they don't reduce under λ (and CBN not inside arguments). Use normal order for full normal forms.
  • Tests take much longer than about 4 s: check you didn't raise the property tests' maxSize. Looping terms grow until the cap (see DECISIONS.md).

07Brain Exercise

Think before you reveal

Random terms almost never separate the two orders (the demo found 0 of 2000). Design, from scratch, (1) a term where applicative order is strictly faster than normal order, and (2) a term where normal order finishes and applicative order never does. What single feature does each term need?

The Lab's checker recognizes both
Reveal the answer

(1) A function that uses its argument more than once, given an argument that still has work in it: (λx. x x) ((λy. y) z), 2 steps vs 3. The feature is duplication. Normal order copies unevaluated work.

(2) A function that ignores its argument, given an argument that never finishes: (λx. y) Ω, or any (λd. t) Ω. The feature is discarding. Applicative order does work nobody needs, and here that work is infinite.

Random terms rarely have both "a function that discards" and "a divergent argument" in the right places, which is why a fair experiment has to plant the situation. Real languages meet it constantly: if c then e1 else e2 must not evaluate both branches, which is why every strict language special-cases if. Module 13 builds if from λ and watches exactly this.

08There Are No Dumb Questions

If normal order is complete, why doesn't every language use it?

Duplication. Normal order can repeat work exponentially often. Haskell uses call-by-need: normal-order-like choice, plus sharing so each argument is evaluated at most once (Module 22).

Is call-by-value the same as applicative order?

Close, but no. Both evaluate arguments first, but CBV never goes under a λ. λx. (λy. y) x is already a value for CBV (0 steps), while applicative order reduces inside it.

Why did 3 random terms reach no normal form under either order?

Within the limits (fuel and size cap), they either loop or grow too large. The demo can't tell you which, because that's undecidable in general. "Within the limits" is doing honest work in that sentence.

Does "different normal forms: 0" prove that normal forms are unique?

No, it's evidence on 2000 terms. The proof is the Church–Rosser theorem, which Module 10 explores by drawing every reduction path of a term and watching them meet.

09What's Next

Every strategy that finished agreed on the answer. Coincidence? Module 10 stops choosing and explores all choices at once: the reduction graph of a term, with every path drawn. It tracks residuals (what happens to one redex when you fire another) and checks Church–Rosser empirically: whenever paths fork, they can be brought back together.
