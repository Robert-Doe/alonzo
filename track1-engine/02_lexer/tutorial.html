01The Big Analogy

A lexer is a supermarket cashier working a conveyor belt.

Items arrive one at a time, in a line: characters. The cashier doesn't care what meal you're planning. Their job is to turn the belt into receipt lines:

  • Grouping. Loose apples keep going into the same bag until something that isn't an apple arrives. That's one receipt line, "apples." The lexer does the same with letters: acc_2 is one line, identifier "acc_2". This is maximal munch.
  • Throwing away dividers. The plastic bars between customers' items don't go on the receipt. Neither do spaces, tabs, newlines or -- comments.
  • Stamping positions. Each receipt line notes where on the belt the item was: line 1, column 7.
  • Handling the unscannable. An item with no barcode (+, $, 42) doesn't shut down the register. The cashier sets it aside, writes down exactly where it was, and keeps scanning.
  • "TOTAL." Every receipt ends with a final line, even an empty one. That's the eof token.

Note what the cashier does not check: whether your groceries make a sensible meal. ) ) λ . ( lexes perfectly well into five tokens. Deciding whether tokens form a term is the parser's job (Module 3).

02What Happens, Step by Step

  1. tokenize(src) starts at offset 0, line 1, column 1.
  2. It looks at the current character, as a whole Unicode code point, so an emoji counts as one character.
  3. Whitespace is skipped. -- skips everything up to the newline.
  4. λ or \ becomes a lambda token. ., ( and ) each become their own token.
  5. A letter or _ starts an identifier. The lexer keeps consuming letters, digits, _ and ' until one can't belong (maximal munch).
  6. A digit starts a number, which the pure calculus doesn't have. The whole run is reported as one error and skipped.
  7. Anything else is reported as an error with its code point, skipped, and lexing continues.
  8. At the end, an eof token is appended. The result is { tokens, errors }. It never throws.

04The Code, Explained

One loop, one decision per character

src/lexer.ts (abridged)

while (offset < src.length) {
  const c = peek();
  const start = pos();
  if (isSpace(c)) { advance(); continue; }
  if (c === "-" && src[offset + 1] === "-") { /* skip to end of line */ }
  if (c === "λ" || c === "\\") { advance(); tokens.push({ kind: "lambda", text: c, start, end: pos() }); continue; }
  // ... ".", "(", ")" the same way ...
  if (isIdentStart(c)) {
    while (offset < src.length && isIdentPart(peek())) advance();   // maximal munch
    tokens.push({ kind: "ident", text: src.slice(start.offset, offset), start, end: pos() });
    continue;
  }
  // ... digits → one "numeric literal" error; anything else → "unexpected character" ...
}
tokens.push({ kind: "eof", text: "", start: pos(), end: pos() });

The inner while is the entire maximal-munch rule: keep eating while the next character could continue a name.

Columns vs offsets: two different counters

const peek = (): string => {
  const cp = src.codePointAt(offset);
  return cp === undefined ? "" : String.fromCodePoint(cp);
};
const advance = (): string => {
  const c = peek();
  offset += c.length;                              // UTF-16 units: 1 for "λ", 2 for "😀"
  if (c === "\n") { line++; col = 1; } else { col++; }   // always +1 per visible character
  return c;
};

JavaScript strings are sequences of UTF-16 units, and an emoji is two of them. offset must count units, because it's used to slice the string. col counts characters, because it's shown to humans.

Errors are values

errors.push({ message: `unexpected character '${c}' (U+…)`, start, end: pos() });

No throw. The lexer records the problem and moves on, so a single run shows all the bad characters. formatError then renders a record the way GCC and rustc do:

1:7: unexpected character '+' (U+002B)
  λx. x + y
        ^
BULLET POINTS
  • Tokens = the terminals of the grammar: λ . ( ) and identifiers, plus an eof sentinel.
  • Maximal munch: an identifier is the longest run of name characters.
  • Positions are recorded at the source, the only place they're cheap to get.
  • Errors are data. Report, skip, continue.

05Limits: What You Cannot Do Yet

Can't do yet

  • Build a tree. Tokens are still flat (Module 3).
  • Detect structural mistakes: λ . ) lexes without complaint.
  • Write numbers or let. Those arrive as encodings (Module 14) and sugar (Module 12, Track 2).
  • Align carets under tabs or wide CJK characters. Columns are code points, not display cells.

Can do now

  • Read raw text in either λ spelling, with any spacing and -- comments.
  • Point to the exact line:col of every token and every bad character.
  • Report all lexical errors in one pass.
  • Guarantee that anything Module 1's printer emits lexes cleanly (tested on 1000 terms).

07Brain Exercise

Think before you reveal

Barendregt's book and many lecture notes write λxy.x and mean two binders, λx.λy.x: the K combinator. Our lexer turns λxy.x into one binder named xy, whose body mentions a free x. That's a completely different term.

Was that a bug or a choice? What would you lose if the lexer split xy into x and y, and how does a user of our lexer still write K without the dots between binders? Predict the tokens of λxy.x and f'x in the Lab's quiz before you reveal.

Take the prediction quiz
Reveal the answer

It's a choice, one that every programming language makes the same way. The textbook convention only works if every variable is a single letter. Then xy can only mean "x then y." Adopt it and you can never name anything succ, acc or f2: succ would lex as four variables, s u c c. Real prelude definitions (Module 12) need multi-letter names.

Maximal munch keeps multi-letter names, and the cost is a space: write λx y. x. The space ends the first identifier. Module 3's parser accepts several binders after one λ, so λx y. x becomes λx. λy. x. And f'x? Also one identifier, because ' and x can both continue a name.

The general lesson: a lexer's grouping rule is part of the language definition. Change it and different programs mean different things. That's why C's x+++y parses as (x++) + y. Maximal munch grabs ++ first.

08There Are No Dumb Questions

Why not let the parser read characters directly?

You can. That's called scannerless parsing. But then every grammar rule has to worry about spaces and comments. Separating them means the parser's grammar talks about clean tokens only. For Track 2's bigger language, the split pays off a lot.

What's the point of an eof token? The array just ends.

It makes "what's next?" always answerable. The parser never reads past the end, and an error like "expected ) but found end of input" gets a real position. It's a sentinel: a fake element that removes a special case.

Why keep going after an error? Isn't the input already broken?

For the user's sake. Fix-rerun-fix-rerun for three typos is miserable. The lexer can safely continue because it has no memory beyond "where am I," so skipping one bad character can't confuse it. Parsers have a harder time recovering (Module 3 discusses why).

Why are columns and offsets different numbers?

Offsets index JavaScript's UTF-16 string, and an emoji takes two slots. Columns are for humans, and an emoji is one character. For λ they agree (λ is a single UTF-16 unit), which is why you rarely notice.

Why does 42 get its own error message?

Because a newcomer typing f 42 deserves to know why it fails: the pure calculus has no numbers, and they're built in Module 14. A generic "unexpected '4'" would leave them guessing.
