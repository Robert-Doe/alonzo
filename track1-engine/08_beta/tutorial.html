From the course: capture-avoiding substitution (Module 5) does the actual work, and Module 7 finds where. New words are in the vocabulary web: redex, contractum, context, reduct.

01The Big Analogy

A reduction step is a mechanic swapping one part in a running engine.

The mechanic doesn't rebuild the car. They unbolt exactly one part (the redex), carry it to the bench, rebuild it there (the contractum), then bolt it back into the same socket. The car with the empty socket is the context, and the car afterwards is the reduct.

Two details the analogy makes vivid. First, the bench work (substitution) must not mix up two bolts that happen to share a label: that's capture avoidance. Second, bolting the part back in must connect it to whatever is around the socket. A part installed under a λ is supposed to plug into that λ's variable. So plugging deliberately does not avoid capture.

02What Happens, Step by Step

  1. Choose a redex by its path (from Module 7's list).
  2. decompose(t, path) walks down the path, building a context one layer per step: appL, appR or lam. What's left at the bottom is the redex.
  3. contract(redex) applies the rule at the root: β gives subst(body, x, arg), and η gives the function part.
  4. plug(context, contractum) rebuilds the term around the result. That's the reduct.
  5. The layers of the context, read from the outside in, are exactly the congruence rules of the step's derivation, ending with β or η.
  6. oneStepReducts(t) does this once per redex, giving every term reachable in one step.

03The Map: A Step, Dissected

04The Code, Explained

Contexts: one constructor per congruence rule

src/reduce.ts

export type Ctx =
  | { kind: "hole" }
  | { kind: "appL"; ctx: Ctx; arg: Term }     // C N     (the hole is in the function)
  | { kind: "appR"; fn: Term; ctx: Ctx }      // M C     (the hole is in the argument)
  | { kind: "lam"; param: string; ctx: Ctx }; // λx. C   (the hole is under a binder)

export function plug(c: Ctx, t: Term): Term {
  switch (c.kind) {
    case "hole": return t;
    case "appL": return App(plug(c.ctx, t), c.arg);
    case "appR": return App(c.fn, plug(c.ctx, t));
    case "lam": return Lam(c.param, plug(c.ctx, t));
  }
}

No renaming anywhere in plug. That's correct, and the test "plugging DOES capture" checks it: λx. □ filled with x must be λx. x.

The rule itself

export function contract(r: Term, log?: SubstLog): Term {
  if (isBetaRedex(r) && …) return subst(r.fn.body, r.fn.param, r.arg, log);   // β
  if (isEtaRedex(r) && …) return r.body.fn;                                  // η
  throw new Error(`${print(r)} is not a redex`);
}

One step = decompose, contract, plug

export function stepAt(t: Term, path: Path, kind?: RedexKind): StepResult {
  const { ctx, focus } = decompose(t, path);
  // … check focus really is a redex of that kind …
  const contractum = contract(focus, log);
  return { path, kind: k, ctx, redex: focus, contractum, reduct: plug(ctx, contractum), renames: log.renames };
}
BULLET POINTS
  • A step is C[redex] → C[contractum], and the result is the reduct.
  • Contexts have one constructor per congruence rule, so a context is the step's derivation.
  • Substitution avoids capture. Plugging deliberately doesn't.
  • The order you pick redexes in changes how many steps you take (Brain Exercise).

07Brain Exercise

Think before you reveal

Start from (λx. x x) ((λy. y) z). It has two redexes: the outer one (ε) and the inner (λy. y) z (arg).

How many steps does it take to reach normal form if you always pick the outer redex first? And the inner one first? Explain the difference in one word. Then do both in the Lab, whose checker counts your steps.

Race both orders in the Lab
Reveal the answer

Outer first: 3 steps. (λy. y) z ((λy. y) z) → z ((λy. y) z) → z z. The outer step copied the unevaluated argument into both places x occurs, so its work had to be done twice.

Inner first: 2 steps. (λx. x x) z → z z. The argument was simplified once, then copied.

The word is duplication. It's the central tension of Module 9: evaluating arguments first avoids duplicated work, but evaluating an argument that's never used can waste work, or even never finish. Module 22 (call-by-need) gets the best of both by sharing instead of copying.

08There Are No Dumb Questions

Why build contexts at all, when a path already says where the redex is?

Because the context is what the textbook rule actually talks about: C[R] → C[R']. As data, it prints (λx. □ z), it tells you the derivation (ξ ∘ app-L ∘ β), and later modules reuse it: evaluation contexts drive the CEK machine (Module 21).

Isn't plugging just substitution for the hole?

No. Substitution replaces free variables and must avoid capture. Plugging fills a hole and must allow it. Mixing them up either breaks steps under λ or reintroduces Module 5's bug. The vocabulary web has a card for exactly this.

Does a step always make the term smaller?

No. (λx. x x x) (λx. x x x) grows with every step, and Ω stays the same size forever. "Reduction" means applying the rule, not shrinking.

Why cross-check against de Bruijn again?

Because β is the one operation everything else trusts. Two implementations that share no substitution code agreeing on 2306 steps is much stronger evidence than either one's own tests.
