01The Big Analogy

A recursive-descent parser is an office of clerks who can hire more clerks.

Tokens arrive on a conveyor belt. There are three kinds of clerk, one per grammar rule:

  • The Row Clerk (term) collects a row of items and clips them together left to right: (a b) c. They stop when the belt shows ) or runs out.
  • The Recipe Clerk (λ) takes the λ, writes down parameter names until the ., then hires a brand-new Row Clerk for the body and waits. That new Row Clerk has no idea where the recipe "should" end, so they keep collecting until ) or the end. That's why a λ-body extends as far right as possible.
  • The Atom Clerk takes a single name, or on seeing (, hires a new Row Clerk for the inside and then insists that the next item on the belt is ).

Every clerk who hires another stops and waits for the finished sub-assembly. The pile of waiting clerks is the call stack. When the last clerk returns, the first Row Clerk is holding the whole tree.

Now remember Module 1's phone call: the printer adds "hold on, these go together" exactly where a listener would otherwise guess wrong. The parser is that listener, with fixed guessing rules. This module checks that the speaker and listener agree on thousands of phone calls.

02What Happens, Step by Step

  1. parse(src) runs the lexer. If there are lexical errors, it returns them and stops.
  2. parseTerm checks that the next token can start an item (a name, ( or λ). Otherwise: "expected a term."
  3. It parses one item, then loops. While the next token can start another item, it parses it and sets acc = App(acc, item). That's the left fold.
  4. An item starting with λ goes to parseLambda: it collects one or more names, requires ., then calls parseTerm for the body, which eats the rest of the row.
  5. An item starting with a name or ( goes to parseAtom. A ( triggers a nested parseTerm and then requires ).
  6. Back at the top, the next token must be eof. Otherwise: "unexpected … after a complete term."
  7. The first syntax error unwinds everything and returns { term: null, errors: [thatError] }.

04The Code, Explained

The row: a loop, not left recursion

src/parser.ts

function parseTerm(): Term {
  return rule("term", () => {
    if (!startsItem(peek().kind)) fail(`expected a term, found ${describe(peek())}`);
    let acc = parseItem();
    // A λ item consumes the rest of the row, so after one, startsItem is false and we stop.
    while (startsItem(peek().kind)) acc = App(acc, parseItem());
    return acc;
  });
}

The textbook rule "term ::= term item" is left-recursive. Written as a function, it would call itself before reading any token, forever. The loop builds the same left-leaning tree, App(App(a, b), c), iteratively. This is convention 1.

The λ: hire a Row Clerk for the body

function parseLambda(): Term {
  return rule("lambda", () => {
    next(); // λ
    const params: string[] = [];
    if (peek().kind !== "ident") fail(`expected a parameter name after 'λ', found ${describe(peek())}`);
    while (peek().kind === "ident") params.push(next().text);
    expect("dot", `after the parameter${params.length > 1 ? "s" : ""} of 'λ${params.join(" ")}'`);
    const body = parseTerm();                                  // ← convention 2 lives here
    return params.reduceRight<Term>((b, p) => Lam(p, b), body);   // λx y. M → λx. λy. M
  });
}

The body is a whole term, not an atom, so it runs until something stops a row: ) or the end. That single call is the "λ extends as far right as possible" convention.

The atom: parentheses reset everything

if (t.kind === "lparen") {
  next();
  const inner = parseTerm();
  if (peek().kind !== "rparen") fail(`expected ')' to close the '(' at ${at(t.start)}, found ${describe(peek())}`);
  next();
  return inner;
}

Parentheses produce no node. They just start a fresh parseTerm. That's why ((λx.(x))) parses to exactly I.

Testing the printer with the parser

src/parens.ts (core)

const without = src.slice(0, open) + " " + src.slice(open + 1, close) + " " + src.slice(close + 1);
const r = parse(without);
const same = r.term !== null && equalSyntax(r.term, original);

To judge a pair of parentheses, delete it and re-parse. (A space goes where each paren was, so (f)(x) can't fuse into the single name fx.) If the tree is unchanged, the pair was decoration.

BULLET POINTS
  • The grammar functions mirror the grammar rules. Read one and you've read the other.
  • Convention 1 is the while loop's left fold. Convention 2 is "the λ-body is a full term."
  • One token of lookahead is enough. The parser never backtracks.
  • The first syntax error ends parsing, with a message naming what was expected and what was found.

05Limits: What You Cannot Do Yet

Can't do yet

  • Know which variables are bound or free. λx. y parses fine, and nobody checks y (Module 4).
  • See that λx. x and λy. y are the same function (Module 4).
  • Name definitions (id = λx. x). That's Module 12.
  • Recover after a syntax error to report a second one.
  • Parse extremely deep nesting. Each ( uses host stack frames (P3.5).

Can do now

  • Type terms as text: (\x y. x) a b.
  • Get precise, located syntax errors.
  • Watch the recursive descent via { trace: true }.
  • Trust the printer: 5000 round trips, and every printed paren is necessary.
  • Ask which parentheses in any text are redundant.

07Brain Exercise

Think before you reveal

Take this text:

(f (λx. x)) ((λy. y) z)

(1) For each of the four parenthesis pairs, is it necessary or redundant on its own? (2) If two pairs are each redundant on their own, can you always delete both? Decide using only the two conventions and Module 1's three-row table. Then check your guesses in the Lab's paren explorer and use "remove ticked pairs together."

Check it in the Lab
Reveal the answer
  1. (f (λx. x)): redundant. It's an application in function position, and convention 1 groups f … … that way anyway.
  2. (λx. x): redundant in this text. Inside pair #1 it's the last thing before ), so nothing follows it to swallow.
  3. ((λy. y) z): necessary. It's an application in argument position. Without it, f … (λy. y) z passes z to f.
  4. (λy. y): necessary. It's a λ in function position. Without it, the body swallows z.

(2) No. Delete #1 and #2 together and you get f λx. x ((λy. y) z): the λ is no longer protected by #1's closing ), and it swallows the rest. Pair #2 was redundant only because #1 was there. Whether a parenthesis is necessary depends on its context, including the other parentheses. That's the same lesson as Module 1's trailing flag, seen from the listener's side. The Lab and node both confirm it: print() writes this tree as f (λx. x) ((λy. y) z), keeping exactly one of the two.

08There Are No Dumb Questions

Why not write the grammar rule term ::= term item directly as a function?

Because parseTerm would immediately call parseTerm, which calls parseTerm… without consuming a token, until the stack overflows. Recursive descent can't handle left recursion. The standard fix is to rewrite it as repetition (item+) and fold the results left.

The lexer reports all its errors. Why does the parser stop at the first?

Because after a structural error the parser genuinely doesn't know what you meant. Was the missing ) meant after x or after y? Every later "error" might be a phantom caused by its guess. Compilers for big languages resynchronize at statement boundaries like ;. A single λ-term has none, so one precise error is more useful than several unreliable ones.

Does 5000/5000 round trips prove the printer is unambiguous?

It's strong evidence, not a proof. The proof is a structural induction (P5) over the three cases of print, showing each emitted string parses back to the same node given the trailing context. The random tests would catch any case where that argument has a hole. They're how we'd find a bug in the proof.

Why does (λx. x) y need parentheses but f (λx. x) doesn't strictly need them?

In the first, the λ is in function position. Something (y) follows it, and the λ-body would swallow it. In the second, the λ is last, so there's nothing to swallow. Our printer writes f λx. x, and the parser accepts that because it allows a λ as the last item of a row.

Why doesn't the tree record where the parentheses were?

Because they don't mean anything once the structure is known. That's the "abstract" in abstract syntax tree. If you wanted to reformat code while preserving a user's parentheses, you'd need a concrete syntax tree instead, as code formatters use.
