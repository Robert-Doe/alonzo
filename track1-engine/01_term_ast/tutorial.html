01The Big Analogy

A λ-term is a stack of recipe cards clipped together, and printing it is reading that stack aloud over the phone.

There are exactly three kinds of card on your kitchen table:

  • An ingredient slip with just a name on it: "x." That's a variable.
  • A recipe card whose header says "Given an ingredient, call it x:" and whose body is another card (the instructions). That's an abstraction, λx. body. The header doesn't say what x is. It's a blank waiting to be filled.
  • A paper clip joining two cards: "use this card (left) on that one (right)." That's an application, fn arg.

Clip cards inside cards inside cards, and you have a tree. On the table, the structure is obvious: you can see which clip holds what.

Now phone a friend and describe the stack so they can rebuild it. Words come out one at a time, flat. If you say "recipe given x: x, clipped to y," did the clip go inside the recipe's instructions, or around the whole recipe? Your friend will guess, and may guess wrong. So you add "hold on, these go together" exactly where the listener would otherwise guess wrong. Those are parentheses.

This module builds the table (the tree data type) and the phone call (the printer). The printer's job is subtle: say "these go together" only when needed, but every time it's needed.

Where the analogy stops

Real recipe cards contain ingredients. A λ-term contains only cards: there is no flour, no number, no string. Even "data" will be built out of cards (Phase 3). And the listener's guessing rules aren't arbitrary. They're the two fixed conventions from P4.3.

02What Happens, Step by Step

  1. You build a term with constructor calls: App(Lam("x", Var("x")), Var("y")). There's no parser yet.
  2. Each constructor checks the name is a legal identifier (e.g. x, f', acc_2) and returns a frozen-shape object tagged var, lam or app.
  3. Nested calls produce a tree. Nothing is ever mutated. A new term is always a new tree, possibly sharing old subtrees.
  4. print(t) walks the tree top-down, carrying one bit of context, trailing ("does anything follow me?").
  5. At each node it emits the node's text and adds parentheses in exactly three situations (section 04).
  6. Alternative views, printFull, show and renderTree, print the same tree in other ways. Measurements (size, depth, counts) walk it with one case per node kind.

04The Code, Explained

The whole language in one type

src/term.ts

export type Term =
  | { readonly kind: "var"; readonly name: string }
  | { readonly kind: "lam"; readonly param: string; readonly body: Term }
  | { readonly kind: "app"; readonly fn: Term; readonly arg: Term };

Three lines, one per grammar production (P4.1). The type is recursive: body, fn and arg are themselves Terms. That's what makes it a tree. Every field is readonly because later modules share subtrees between old and new terms, which is only safe if nobody edits a node.

Every function has the same skeleton

src/term.ts

export function size(t: Term): number {
  switch (t.kind) {
    case "var": return 1;
    case "lam": return 1 + size(t.body);
    case "app": return 1 + size(t.fn) + size(t.arg);
  }
}

One case per node kind, recursing into the children. You'll write this skeleton roughly a hundred times in this course: for free variables, substitution, reduction, type checking, compiling. Get comfortable with it now.

The printer: three rules and one bit of context

src/print.ts

function go(t: Term, trailing: boolean): string {
  switch (t.kind) {
    case "var":
      return t.name;
    case "lam": {
      const s = `${L}${t.param}. ${go(t.body, true)}`;
      return trailing ? s : `(${s})`;
    }
    case "app": {
      const fn = go(t.fn, false);
      const arg = t.arg.kind === "app" ? `(${go(t.arg, true)})` : go(t.arg, trailing);
      return `${fn} ${arg}`;
    }
  }
}

Read it against the three required-parenthesis situations:

SituationWhere in the codeWithout the parens you'd get…
A λ in function positiongo(t.fn, false) → the λ case sees trailing=falseλx. x y: the body swallows y
An application in argument positiont.arg.kind === "app" ? `(…)`f a b: regrouped as (f a) b
A λ argument with something after itgo(t.arg, trailing) passes the context downf λx. x g: the λ swallows g

Why does a λ's body get trailing = true? Because by the second convention a body runs to the end of whatever contains the λ, so nothing can follow it inside the λ.

BULLET POINTS
  • The tree is the truth. Text is a lossy transport format that needs parentheses to survive the trip.
  • Parentheses are needed in exactly three situations, all derived from two textbook conventions.
  • One of them can't be decided by looking at a node alone. It depends on what comes after it.

05Limits: What You Cannot Do Yet

Can't do yet

  • Read text. "λx. x" can't become a tree until Module 3.
  • Prove the printer is unambiguous. That needs parse(print(t)) = t (Module 3).
  • Tell that λx. x and λy. y are the same function. equalSyntax says no (Module 4 fixes this).
  • Compute anything. There's no reduction until Module 8.

Can do now

  • Represent every λ-term as a tree.
  • Print any tree in textbook notation, fully-parenthesized form, ASCII, constructor form, or as a drawn tree.
  • Measure size, depth and node-kind counts.
  • Generate reproducible random terms for property tests.

07Brain Exercise

Think before you reveal

Most of the printer decides parentheses by looking at a node and its immediate parent. But the λ case takes an extra argument, trailing, which comes from further away.

Find two terms that contain the identical λ subtree, such that the correct printout needs parentheses around it in one term and none in the other, even though its parent node is the same kind (an application) in both. What does that tell you about whether a "local" printer (one that only looks at a node and its parent's kind) could ever be correct?

Then test your answer: in the Lab, build each term and use Pin as A / Pin as B. The checker verifies it.

Check it in the Lab
Reveal the answer

Take λx. x as the argument of an application in both terms:

  • App(Var f, Lam x x) prints f λx. x. The λ is last, so its body can't swallow anything.
  • App(App(Var f, Lam x x), Var g) prints f (λx. x) g. The inner application is the function part of an outer one, so g follows it.

In both, the λ's parent is an application and the λ is that parent's argument. The difference is two levels up: whether the parent is itself followed by something. So no local rule can decide it. Information must flow down the recursion, and that's the trailing flag. Compiler writers call such a flag an inherited attribute: a value passed from parent to child during a tree walk. You'll see many more of them, such as the binding environments in Module 19 and the typing contexts in Module 24.

08There Are No Dumb Questions

Why not just store terms as strings, like "λx. x y"?

Because every operation you'll write (renaming, substitution, reduction, typing) asks structural questions: "what's the body of this λ?" "what's the argument?" On a string you'd re-parse every time, and you'd constantly be one bracket away from a bug. Trees answer structural questions in O(1).

Where are the numbers? How do I write 2 + 3?

You can't, yet, and in the pure λ-calculus you never get built-in numbers. Numbers become particular functions (Church numerals, Module 14). That's the λ-calculus's most surprising claim: functions alone are enough.

equalSyntax(λx. x, λy. y) says false. Isn't that wrong?

For the λ-calculus, yes. They're the same function (P2.5). equalSyntax answers a narrower question: "are these literally the same tree, names included?" Module 4 adds α-equivalence for the real question. Keeping both makes the difference explicit.

Books write Ω as (λx. x x)(λx. x x). Why does ours drop the second pair?

Because it's the last thing in the term, nothing follows the second λ that it could swallow. Both spellings denote the same tree. Ours is the minimal one. Minimal output is a convention we chose (see DECISIONS.md, category (c)) to make the rules visible.

Why does a λ have only one parameter? I want λx y. ….

By definition every λ binds exactly one variable, and multi-argument functions are curried (P1.4). λx y. M is only shorthand for λx. λy. M. The helper lams(["x","y"], M) builds that nesting, and Module 3's parser will accept the shorthand.

09What's Next

You can hold a term and print it, but you still have to type App(Lam("x", Var("x")), Var("y")) to get one. Humans want to type (\x. x) y. Getting from characters to a tree takes two steps, and Module 2 builds the first: a lexer that chops raw text into tokens (λ, identifiers, ., parentheses), remembers where each came from, and reports a precise, located error on bad input instead of crashing. Module 3 then assembles the tokens into this module's trees, and finally proves the printer is unambiguous.
