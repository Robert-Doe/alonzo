MODULE 07

Redex Anatomy

Before an engine can compute, it must answer one question: where in this term can a step happen? The answer has an exact, finite shape: the redexes.

01The Big Analogy

A redex is a sealed envelope stapled to its letter.

A λ-abstraction is an envelope with instructions inside: "whatever you give me, call it x, then…". An application M N staples a letter N to M. If M is an envelope, the pair is ready to be opened: tear the envelope, drop the letter in wherever the instructions say "x". That ready-to-open pair, (λx. …) N, is a β-redex.

If M is just a name (f N), there's nothing to open. You're holding a letter addressed to someone who isn't here. A term can contain many ready envelopes, nested and side by side. This module doesn't open any. It walks the whole pile and makes a numbered list: where each ready envelope is, which is first in reading order, which are innermost, and which one sits at the very head of the pile.

The second shape, the η-redex λx. M x, is an envelope whose instructions are only "forward whatever you get to M". It's a middleman that can be removed. More on η in Module 11.

02What Happens, Step by Step

  1. findRedexes(t) walks the tree in pre-order: node, then function part, then argument.
  2. At each node it asks: is this an application whose function is a λ? If so, it records a β-redex with its path.
  3. If η was requested, it also asks: is this λx. M x with x not free in M?
  4. Pre-order means the list is already in reading order, outer before inner. The first entry is the leftmost-outermost redex.
  5. The leftmost-innermost is the first entry that contains no other redex (no other path extends its path).
  6. The head redex: skip leading λs, then walk down the function spine. If the head of the spine is a λ, the application just above it is the head redex.
  7. No β-redexes at all means the term is in β-normal form: finished.

04The Code, Explained

The whole finder is one pre-order walk

src/redex.ts

export function findRedexes(t: Term, kinds = ["beta"]): Redex[] {
  const out: Redex[] = [];
  (function go(u: Term, path: Step[]): void {
    if (wantBeta && isBetaRedex(u)) out.push({ kind: "beta", path: [...path], term: u });
    if (wantEta && isEtaRedex(u)) out.push({ kind: "eta", path: [...path], term: u });
    if (u.kind === "lam") go(u.body, [...path, "body"]);
    else if (u.kind === "app") { go(u.fn, [...path, "fn"]); go(u.arg, [...path, "arg"]); }
  })(t, []);
  return out;
}

Record the node before visiting its children, and visit the function before the argument. That order is reading order.

The two shapes

export function isBetaRedex(t: Term) { return t.kind === "app" && t.fn.kind === "lam"; }
export function isEtaRedex(t: Term) {
  return t.kind === "lam" && t.body.kind === "app" && t.body.arg.kind === "var"
    && t.body.arg.name === t.param && !freeVars(t.body.fn).has(t.param);
}

The last condition matters: λx. x x looks like "forward x to something," but that something is x itself. It isn't a middleman.

The head: walk down the spine

function spineRedex(u: Term, path: Step[]): Redex | null {
  while (u.kind === "app") {
    if (u.fn.kind === "lam") return { kind: "beta", path: [...path], term: u };
    path.push("fn");
    u = u.fn;
  }
  return null;
}

M N1 N2 N3 is ((M N1) N2) N3. The spine is the chain of fn links, and M is at the bottom. If M is a λ, the application holding it is the head redex. If M is a variable, the loop falls off the end: no head redex, no matter what's in the arguments.

BULLET POINTS
  • β-redex: an application whose function is a λ. η-redex: λx. M x with x not free in M.
  • Pre-order lists redexes in reading order, so the first is leftmost-outermost.
  • The head redex, if there is one, is the leftmost-outermost redex (tested on 3000 terms).
  • No β-redexes = β-normal form. A variable at the head = head normal form, even with redexes elsewhere.

The tests show that whenever a term has a head redex, it is the leftmost-outermost redex.

So can a term have redexes but no head redex at all? If so, write one. What does that tell you about whether any amount of computation could change the "outline" of that term? The Lab's checker reads whatever term you type.

Reveal the answer

Yes. Any term whose head is a variable: x ((λa. a) b) ((λc. c) d) has two redexes but no head redex (the demo shows it). Its shape is "x applied to two things," and x is not an envelope, so nothing can ever be opened at the head.

Contracting redexes in the arguments changes the arguments, never the fact that the whole term is x □ □. That fixed outline is called head normal form, and it's why HNF is the right notion of "a meaningful answer" in the theory of the λ-calculus (Module 11, and Böhm trees in Module 34). Lazy evaluators stop even earlier, at weak head normal form, and don't bother with the arguments until they're needed.

08There Are No Dumb Questions

Why is it called a "redex"?

It's short for reducible expression, the term-rewriting word for a sub-term matching the left side of a rule (P6.1). What it becomes after the step is the contractum (Module 8).

Is f ((λx. x) y) a redex?

The whole thing isn't (its function part is f, a variable), but it contains one: (λx. x) y at path arg. "Redex" always refers to the exact sub-term.

Why do we need both "outermost" and "innermost"?

Because they give the two classic evaluation orders. Outermost-first is normal order (and, roughly, lazy languages). Innermost-first is applicative order (and, roughly, strict languages like OCaml and JavaScript). Module 9 races them, and one of them loops forever on a term the other finishes.

Can two redexes overlap without one being inside the other?

No. A redex is a sub-tree, and two sub-trees are either nested or disjoint. That's why path prefixes are enough to decide "inside."
